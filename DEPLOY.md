# Deploy — status and what to watch

The app is live on Fly.io (`fly launch` was run after Phase 3 merged, generating `fly.toml` and
`.github/workflows/fly-deploy.yml`). This file now tracks operational notes rather than a
pre-deploy checklist.

## What happened after the Phase 3 PR merged

- `fly launch` ran against the hand-written `fly.toml` from Phase 3, registered the app, and
  added `.github/workflows/fly-deploy.yml` (its own deploy workflow, distinct from the
  `deploy.yml` this repo had before — see "Workflow cleanup" below).
- The first deploy went out on merge — but **`CI` was failing on that same commit**, and the
  original `fly-deploy.yml` (as generated by `fly launch`) deploys unconditionally on push to
  `main`/`master`, with no dependency on CI passing. So a red build shipped. Fixed below.

## Bug: CI was failing on a clean checkout

`bun run check` failed in CI (but not locally) with:

```
Database not found at ./output/licenses.db. Run: bun run parse
```

Cause: `web/repository.ts` used to open `output/licenses.db` and `process.exit(1)` on failure
as a **module-level side effect**, so importing the module — which
`web/__tests__/repository.test.ts` does, to get `Repository` and `buildWhere` — ran that code
too, even though the test seeds its own temporary database and never touches the real one. In
CI, `bun run check` (which runs `bun test`) executes before `bun run parse` builds
`output/licenses.db`, so the file didn't exist yet and the import crashed the whole test
process. Locally this was invisible because `output/licenses.db` was already sitting on disk
from earlier manual runs.

Fix: `web/repository.ts` is now side-effect-free at import time — just the `Repository` class
and `buildWhere`. Opening the real database and failing fast if it's missing moved to
`server.tsx`, the actual entry point, where that side effect belongs. Verified by running
`bun run check` with `DATABASE_PATH` pointed at a nonexistent file (simulating a fresh CI
checkout) — passes now, and `bun server.tsx` under the same broken path still exits with the
same clear "Run: bun run parse" message as before.

## Workflow cleanup: two deploy workflows, one gated

`fly launch` generated `fly-deploy.yml` deploying unconditionally on every push to
`main`/`master` — the pre-existing `deploy.yml` (written in Phase 3, gated on `CI` succeeding
via `workflow_run`) never actually ran anything ("skipped", since its trigger workflow's
conclusion was checked but nothing consumed it — moot point now). Keeping both was actively
harmful: an ungated workflow next to a gated one just means the ungated one wins and nothing
is actually protected.

Resolved by deleting `deploy.yml` and adding the same `workflow_run` gate (CI success required)
to `fly-deploy.yml` instead, so there is exactly one deploy workflow and it only fires after
`CI` succeeds on that commit.

## Fixed: Node 20 deprecation warning

`actions/checkout@v4` triggered `Node 20 is being deprecated ... forced to run on Node.js 24`
in the run logs (GitHub's runners are dropping Node 20 as the action-runtime; `@v4` still
declares it). Bumped to `actions/checkout@v7` (latest, targets a current Node runtime) in both
`ci.yml` and `fly-deploy.yml`. Also pinned `superfly/flyctl-actions/setup-flyctl` from the
floating `@master` to `@v1` while touching that file — `@master` runs whatever's on that
branch right now with no way to pin or audit it.

## Branch protection

`main` now requires the `CI / check` status check to pass before a PR can be merged (set via
`gh api` — see git history / repo settings for the exact ruleset). This is what "check fails,
PR should not be mergeable" actually requires; a passing CI alone doesn't block merges without
this.

## Data: no volume, by design (until it isn't)

`output/licenses.db` is baked into the image at build time from `data/*.csv` — no `[mounts]`
in `fly.toml`, no persistent volume. "Update the data" is: edit `data/*.csv` or
`parser/overrides/*`, push to `main`, CI rebuilds the image (the `data` Docker stage reruns,
`assets` stays cached — verified in Phase 3 by touching each independently and checking which
stage cache-hits), CI passes, `fly-deploy.yml` ships it.

Revisit this (move to a Fly volume + `fly sftp` upload) if any of these become true:

- `output/licenses.db` grows past ~200–300MB
- Data starts coming from somewhere other than git (an external API, a web upload form)
- The running app ever needs to _write_ to the database (it currently only reads)

## Command cheatsheet

```bash
# Build and smoke-test the image locally (needs a Docker daemon — colima on this machine)
colima start   # if not already running
docker build -t geo-kg:local .
docker run -d --name geo-kg-local -p 3000:3000 geo-kg:local
curl -s localhost:3000/ -o /dev/null -w '%{http_code}\n'
docker rm -f geo-kg-local

# Manual deploy (bypassing GitHub Actions)
flyctl deploy --remote-only

# Check current deploy status / logs
flyctl status
flyctl logs
```
